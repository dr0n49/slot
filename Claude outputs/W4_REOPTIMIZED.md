## 0. Проверка семантики `rtp_share` (перед запуском)

Ты просил не принимать число на веру. Разобрал код.

В `game_optimization.py` доли складываются в `P.RTP`:
`basegame_rtp = 0.96 − freegame − "0"`. В Rust (`main.rs`, `parse_fence_info`)
`avg_win = hr × rtp`, а вероятность критерия — `1 / hr`. Значит **`rtp` — абсолютный вклад
критерия в общий RTP**, а не доля от чего-то ещё: `0.535` = 53.5 pp из 96.

Важная тонкость: критерий — это класс **книг целиком**, поэтому `freegame` включает и базовый
спин, который запустил фичу, а не только фриспины. Это не то же самое, что 53.84 pp из
валидации (там разбивка по gametype). Измерил на production, 300 000 честных раундов:

```
общий RTP                     95.458 %
фича-раунды (книги с фичей)   53.300 pp   <- это и есть цель для rtp_share['freegame']
обычные раунды                42.158 pp
   для сравнения, по gametype: база 42.562 pp / фриспины 52.896 pp
нормировка на 0.96:  freegame = 0.5360   basegame = 0.4240
```

**Твоё число корректно** — измеренное 0.536 против согласованного 0.535 (разница 0.1 pp).
Менять не стал, использовал 0.535 как утверждено.

## 5. Насколько приблизились и что осталось

Что починилось:

* **Разделение RTP** — было +40 % / −33 % мимо, стало −0.4 % / −0.8 %. Практически точно.
* **Волатильность** — с 6.92 до 9.46 при цели 11.59: отставание сократилось с 40 % до 18 %.
* **Хвост ×100** — было −60 % от цели, стало +38 %.
* **p99.9 / p99.99** — было −44 % / −58 %, стало −18 % / −34 %.

Что осталось, и почему — три разные причины, не одна.

**(а) Хвост выше ×500 упирается в размер библиотеки, а не в оптимизатор.** В наборе из
200 000 базовых книг:

```
выплата >= x250     1725 книг     >= x500   262 книги
выплата >= x1000      14 книг     >= x1500    1 книга
выплата >= x2000       0 книг     >= x3000    0 книг     максимум в библиотеке 1563x
```

Цель `P(≥×1000) = 0.000339 %` — это событие 1 на 295 000. Оптимизатор не может взвесить
книги, которых нет: на 14 книгах разрешение по этому хвосту физически отсутствует. Чтобы
хвост стал представительным, нужен прогон на **несколько миллионов** книг, а не
перенастройка. Отсюда же и `max observed 1563×` вместо 2465×.

Отдельно: **кап 3000× в опубликованной сборке недостижим** — в библиотеке нет ни одной книги
выше 1563×. Даже натурально лаборатория за 100 млн раундов видела максимум 2465×, так что
3000× — это честный потолок-ограничение, но не выигрыш, который кто-то когда-нибудь получит.
Практический максимум игры — примерно 1 500–2 500×.

**(б) Hit rate завышен на 0.8 pp из-за ещё одной устаревшей цели.**
`BASE_MODE["hit_rate"]["basegame"] = 1.6`, то есть 62.5 % спинов должны быть выигрышами
базовой игры. Измерено натурально: **1 / 1.621**, то есть 61.7 %. Плюс 0.55 % фич — итого
цель должна давать 62.26 %, а даёт 63.06 %. Я это **не менял** (в списке согласованного не
было). Предлагаю `1.6 → 1.621`.

**(в) Середина лестницы просела, верх завышен — остались ручные constraints, о которых я
не написал в прошлом отчёте.** Помимо убранных четырёх правил, в `game_optimization.py`
есть ещё два блока того же рода:

```python
# базовый режим
"distribution_bias": ConstructFenceBias(
    applied_criteria=["basegame"], bias_ranges=[(2.0, 6.0)], bias_weights=[0.5]
)
# бонусный режим
"scaling": ConstructScaling([
    {"criteria": "freegame", "scale_factor": 0.9, "win_range": (20, 60), ...},
    {"criteria": "freegame", "scale_factor": 1.3, "win_range": (300, 1200), ...},
])
```

Это моё упущение — в отчёте W4 я процитировал только базовый `scaling`. Обе подобраны под
старую математику и старый кап: диапазон (300, 1200) у бая и смещение в полосу 2–6× у базы.
Симптомы совпадают: оптимизатор стал предпочитать книги с одним каскадом (43.85 % против
40.08 % у натуральной модели) и книги, где кеги сразу утаскивают шаг на ×10–×50, вместо
книг с 2–3 каскадами. Отсюда просевшие reach ×2 / ×3 / ×5 и раздутый верх.

Убирать их сам не стал — это ровно та же категория изменений, что ты утверждал отдельно.
