## 1. K-4: правило и его проверка

### Правило

Из ступени `i` при `k` кегах каскадный шаг проходит ступени `i … min(i+k, top)` и
**платит один раз за каждую пройденную ступень**:

```
multiplier(step) = Σ ladder[j],  j = i … min(i+k, top)
next_rung        = min(i + k + 1, top)
```

Инвариант: пройденные ступени образуют непрерывный отрезок, каждая из них оплачена ровно
один раз, следующая ступень ровно на одну выше последней пройденной. **Пропуск ступени
невозможен по форме формулы**, а не по договорённости с презентацией.

Пример из задания: старт ×2, два кега →

```
×2 → ×3 → ×5      multiplier = 2 + 3 + 5 = 10,   следующий каскад стартует с ×10
```

### Проверка выплаты для разного числа кегов (лестница B, базовая игра)

| Старт | Кегов | Пройдено ступеней | Последовательность | Множитель шага | Следующая |
|---|---|---|---|---|---|
| ×1 | 0 | 1 | ×1 | 1 | ×2 |
| ×1 | 1 | 2 | ×1 ×2 | 3 | ×3 |
| ×1 | 2 | 3 | ×1 ×2 ×3 | 6 | ×5 |
| ×1 | 3 | 4 | ×1 ×2 ×3 ×5 | 11 | ×10 |
| ×2 | 2 | 3 | ×2 ×3 ×5 | 10 | ×10 |
| ×1 | 6 | 7 | ×1 ×2 ×3 ×5 ×10 ×20 ×50 | 91 | ×50 (потолок) |
| ×1 | 10 | 7 | вся лестница, без повторов | 91 | ×50 |
| ×10 | 30 | 4 | ×10 ×20 ×50 → отрезан потолком | 80 | ×50 |
| ×50 | 3 | 1 | ×50 | 50 | ×50 |

### Юнит-тесты

`mathlab/test_k4.py` — независимая референсная реализация правила на Python плюс сверка с
тем же кодом, который исполняет симулятор (`nvsim --selftest`). Все 14 проверок проходят:

```
ok  start x2 + 2 kegs -> passes x2,x3,x5
ok  0 / 1 / 2 / 3 / 6 kegs at rung 0
ok  cap: 10 kegs from rung 0 stops at the top rung, no repeats
ok  cap: from the top rung a keg pays the top rung once
ok  cap: next rung never exceeds the top
ok  cap: 30 kegs (more than the board can hold) is still bounded
ok  board maximum 30 kegs from rung 0 is the whole ladder
ok  invariants over every (rung, kegs 0..30) on both ladders
ok  C simulator matches the reference on all 140 sampled cases
```

Проверяемые инварианты на всех парах (ступень × 0…30 кегов) на обеих лестницах:
непрерывность отрезка, «каждая пройденная ступень оплачена ровно один раз», корректная
следующая ступень, монотонность (лестница никогда не идёт вниз).

Максимум кегов физически ограничен бордом 5×6 — 30 штук; тесты покрывают этот случай и
всё, что выше потолка лестницы.

## 6. Насколько модель зависит от оптимизатора

Оптимизатор SDK перевешивает симулированные книги, пока взвешенное среднее не попадёт в
целевой RTP. Среди всех перевесовок, удовлетворяющих этому одному ограничению, минимально
искажающая — экспоненциальный тилт `q(x) ∝ p(x)·e^(−λx)` (решение задачи с минимальной
KL-дивергенцией). Реальный оптимизатор, у которого поверх этого ещё квоты и критерии,
искажает **не меньше**. То есть числа ниже — это лучший случай.

## 7. Вердикт

**B + K-4 проходит валидацию.**

* RTP 96.53 % ±0.22 натурально — оптимизатору остаётся 0.53 pp вместо 41.8.
* Лестница стала игровой механикой: ×2 в 41 % раундов, ×3 в 20 %, ×5 в 8.3 %, ×50 в 0.29 %.
  Мёртвых ступеней нет, каждая ступень несёт от 3.0 до 12.1 pp.
* Волатильность 11.59 против 7.90 — современный high-vol профиль.
* Среднее число каскадов 0.955 против 0.728; два и более каскада — 22.3 % раундов против 13.6 %.
* K-4 доказан юнит-тестами: ни одна ступень не может быть пропущена ни математикой, ни презентацией.
* Честный кап — 3 000×; `wincap`-критерий и `FRWCAP` удаляются.
* Честная цена бая — 114–115×.

C остаётся запасным вариантом, если понадобится пятизначный максимум: он лучше по хвосту
(P ≥ ×1000 в 7 раз выше, максимум 8 983×) и по волатильности (13.09), но слабее в середине
лестницы и его фрилестница длиннее.

## 8. Список изменений для W3 (после подтверждения)

В `math_params.py`:

1. `LADDER["basegame"] = [1, 2, 3, 5, 10, 20, 50]`, `LADDER["freegame"] = [2, 4, 8, 16, 35, 80, 200]`.
2. Веса: `R` 28 → 22 (base), 26 → 10 (free); `K` 3 → 3 / 4 → 5; `W` 3 → 3 / 4 → 5.
3. Скаттеры только на барабанах 1/3/5 с точным числом на ленту (3, –, 2, –, 2) — требует
   поддержки пер-барабанного количества в `build_reels.py`.
4. `FS_TRIGGER = {3: 10, 4: 14, 5: 18}`, `FS_RETRIGGER = {3: 5, 4: 7, 5: 9}`.
5. `PAYTABLE_SCALE = 0.070312` (или переписать `PAYTABLE` готовыми значениями — при таком
   мелком множителе шаг квантования 0.01× становится заметной долей выплаты, и чистые
   значения в таблице надёжнее одного коэффициента).
6. `WINCAP = 3000`.
7. `BONUS_COST = 115.0`.
8. Убрать `_WINCAP_WEIGHTS` и ленту `FRWCAP`.

В `game_config.py`: убрать критерий `wincap` из обоих bet mode.

В `game_calculations.py`: `win = round(base * mult, 2)` вместо `max(0.1, round(..., 1))`.

В `game_executables.py`: K-4 — множитель шага как сумма пройденных ступеней, следующая
ступень `min(i + k + 1, top)`; событие `kegBlast` должно нести полный список пройденных
ступеней и выплату на каждой, чтобы презентация ничего не считала сама.

В `gamestate.py`: сбрасывать `ladder_index` в начале каждого фриспина.
